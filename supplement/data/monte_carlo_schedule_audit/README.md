# Saved Monte Carlo schedule and sampler evidence

This addendum makes the actual saved FV-MPC timing records inspectable for all **1,536 zero/hold pairs: 64 repetitions × 24 episodes, with 3,072 distinct case logs**. It also supplies the saved draw indices, the complete 36,000-row FV latency pool, and the exact sampler and scheduler source from the results archive.

## Run the independent offline check

Python 3.10 or later is sufficient; only the standard library is used. From this folder:

```bash
python -B verify_mc_audit.py
```

When integrated at `Supplement_S1/data/monte_carlo_schedule_audit/`, run from S1:

```bash
python -B data/monte_carlo_schedule_audit/verify_mc_audit.py --output outputs/monte_carlo_schedule_audit
```

The command writes `verification_summary.json` and one row for each of the 1,536 pairs in `paired_schedule_checks.csv`. Default output is `outputs/offline/` beside the script. It imports neither the archived experiment code nor a machine-learning library, and performs no model inference or thermal simulation. A mismatch raises an error and gives a nonzero exit status.

The optional full-archive check additionally compares every exported event and draw to its original raw log:

```bash
python -B verify_mc_audit.py --raw-archive /path/to/latency_monte_carlo_20261013T060637Z_results.zip
```

Its default output is `outputs/raw_archive/`. This reads selected members of the 5.10-GB ZIP without extracting temperature fields or quadrature. It also hashes the entire ZIP. The original archive is not required for the ordinary offline check.

## What is original evidence, and what is derived

`actual_schedules.csv.xz` is a projection of each case's own `trace.jsonl.gz`. **Both policy arms are independently exported.** Neither arm is generated by copying the other. Rows are interleaved by pair and original event position only to improve compression; `case_id` and `event_index` recover each original order.

The request, `snapshot_ns`, `ready_ns`, `compute_ready_ns`, `deadline_ns`, `expired`, sampled `delay_ms`, injected-delay values, source-request identifier, token gap, fallback reason, and token count are saved trace fields. Application/deadline-fallback and busy-skip event types, times, and request identifiers are also saved fields. No missing completion time or expiry flag was inferred for the export. `case_id`, `event_index`, and the compressed table layout are new indexing metadata.

These are **realized records of the archived simulation scheduler**. In that experiment the scheduler calculated readiness from sampled measured latency. They are not fresh GPU completion measurements taken during each Monte Carlo rollout. `ready_ns` records planned completion, including beyond a deadline; an expired result is discarded by the simulated policy. `apply` and `deadline_fallback` are the saved command-event records. Some have `no_change=true` in the full log; the present schedule table retains their event time but omits command vectors and `no_change`, which can legitimately differ between policies.

`actual_draws.csv.xz` is a projection of `replay_rows.json.gz`, which contains the sampler's saved records. **The pool offsets and source indices were present in those original records.** The extractor did not invent or backfill them. Repeated fields are factored into explicit dictionaries:

- Each case's saved seed, method, episode, repetition, and sequence are in `cases.jsonl.gz`, under `sampler_context`.
- Each saved pool hash, size, path, fallback reason, and source token count is in `pool_families.json`.
- Each actually used source-row SHA-256 is in `saved_source_row_hashes.csv.gz`, keyed by `source_interleaved_row`.
- The complete original source rows remain in `fv_timing_pool.json.gz`.

Before factoring, extraction checked every repeated context field and every embedded source-row object/hash against its actual saved record. The optional raw-archive check repeats this correspondence independently. Dictionary coding does not replace one policy's observed log with a common draw plan.

The verifier's clock predictions, independently recomputed random offsets, comparison flags, and aggregate counts are **derived checks**, written only under the selected output folder. Original values remain in the input tables.

## Column definitions

All row indices are zero-based. Times are integer nanoseconds from the episode start; latency values are milliseconds. An empty schedule cell means that the field was absent in that event, not zero. A JSON `null` in `fallback_reason` is distinct from an absent field.

### Schedule table

| Columns | Definition |
|---|---|
| `case_id`, `event_index` | New case index and original row position within that case's trace |
| `event` | Original `request`, `apply`, `deadline_fallback`, or `busy_skip` |
| `request` | Original counter of admitted requests; absent for `busy_skip`. This is not the nominal tick number. |
| `snapshot_ns` | Original admitted-request time |
| `ready_ns`, `compute_ready_ns` | Saved result-arrival and computation-completion times; equal in this experiment because injected delays are zero |
| `deadline_ns`, `expired` | Saved request deadline and Boolean expiry (`0` or `1`) |
| `time_ns` | Original apply/deadline-fallback/busy-skip event time |
| `delay_ms` | Measured latency selected for this request, as recorded in the trace |
| `injected_compute_ms`, `injected_apply_ms` | Original injected-delay fields; zero in these cases |
| `trace_request`, `trace_token_gap` | Original selected timing-journal request identifier and token matching gap |
| `fallback_reason`, `tokens` | Original live decision's reason and input-token count used for latency matching |

### Draw table and dictionaries

| Columns | Definition |
|---|---|
| `case_id`, `request` | Join to the case and actual admitted request |
| `pool_family_id` | New dictionary index into saved pool-family metadata |
| `pool_index` | Original recorded offset within the matched empirical pool |
| `source_interleaved_row` | Original recorded index in the 36,000-row FV pool |
| `source_repeat`, `source_request` | Original timing repetition and journal request identifier |
| `token_gap` | Original matching gap |
| `e2e_ms` | Original recorded sampled latency |

`pool_families.json` retains the original `matched_pool_sha256`, `matched_pool_size`, `path`, `fallback_reason`, and `tokens`. The source-row hash dictionary preserves the sampler's recorded hashes. The full SHA-256 draw domain is `(seed, method, episode, replicate, matched_pool_sha256)`; the request counter and rejection-attempt counter complete the hash payload. Policy is absent from the archived domain, which permits the zero/hold pairing.

## Verification and exact tolerances

The offline script checks:

1. Exported input hashes, original case/pool seals, protocol binding, and every archived harness hash.
2. The complete 64 × 24 × 2 case grid, original event order, exactly 600 admitted-or-skipped nominal ticks per case, and counts against each original metrics file.
3. For every request: `ready_ns = snapshot_ns + ceil(delay_ms * 1e6)`, `deadline_ns = snapshot_ns + 100000000`, and `expired = (ready_ns > deadline_ns)`. It also checks zero injected delay, admission/skipping against the previous completion, one event per request at `min(ready_ns, deadline_ns)`, and application-before-request order at coincident ticks.
4. Exact equality between the two actual policy logs for event order, request identity, request/completion/deadline/event times, expiry flags, and sampled/injected delays. Command values and thermal states are outside this equality claim.
5. For every consumed draw in both arms: source reason and nearest-token pool membership, membership hash/size, independent SHA-256 rejection-sampling offset, original source index/repetition/request, saved source-row hash, token gap, and selected latency. It also checks exact paired equality of the consumed draw records.

**No numerical tolerance is applied to integer times, counters, hashes, flags, table projections, or paired records.** Millisecond values are serialized with Python's round-trip float representation and are compared exactly after parsing. The readiness check intentionally uses the archived operation `ceil(delay_ms * 1e6)`, rather than rounding to a nominal precision. The original strict `ready > deadline` rule is used; equality meets the deadline. The pool/object hash serialization and SHA-256 rejection rule follow the documented archived definitions, implemented independently in the verifier.

## Provenance and limits

Source archive: `latency_monte_carlo_20261013T060637Z_results.zip`, root `latency_monte_carlo_20261013T060637Z/`. Selected logs are under `cases/monte_carlo_fv_mpc_delayed_mcXXXX_{zero,hold}_l2_XXXXXX/attempt_.../`. Exact member paths and hashes are recorded per case.

The original protocol pins `harness/latency_replay.py` and `harness/scheduler.py`; `harness/worker.py` verifies those hashes before execution, imports these modules, and writes the saved traces/draw records. The source copies here are byte-for-byte archive members, including their line endings. A case manifest binds its logs to the original protocol SHA-256. This connects the supplied code and saved records to the archived experiment; hashes establish integrity, not independent authentication of how the experiment was performed.

This addendum verifies saved timing/sampling evidence. It does not re-execute inference, the thermal plant, command selection, training, or costs. Full temperature fields, quadrature, model weights, and unused potential preflight draw plans are omitted. The complete measured FV pool is present, so all **consumed** FV draws can be recomputed. Other methods' case logs and timing pools are outside this addendum. Finite-pool uncertainty, serial dependence, hardware variability beyond the recorded timing trials, and model/episode generalization remain outside the experiment's IID sampler.

To recreate the export, run `python -B extract_mc_audit.py /path/to/original.zip --output /path/to/new_audit_folder`. This is a CPU-only archive transformation, not an experiment. The extraction can be slow because the selected compressed trace/draw members total about 1.09 GB; final compact-file sizes and measured verification times are recorded in the accompanying report.
